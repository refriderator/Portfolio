Training a tiny brain for Jarvis

October 18, 2026 · Web

Model: https://huggingface.co/refriderator/jarvis-qwen3-4b

Before Jarvis goes to the cloud, it tries a small AI model running on my Mac. The off-the-shelf model was honestly pretty bad at this, so I fine-tuned my own. I kept its job narrow on purpose: set timers, open apps, arrange windows, do maths with a calculator tool, and say ESCALATE for anything else so Claude can take it.

Fitting it on a laptop

I did all of this on my 24 GB MacBook, so memory was the thing I kept running into. You can estimate a model’s size as parameters × bits per weight. For Qwen3 8B at 4 bits that’s 8 billion × 0.5 bytes ≈ 4 GB (closer to 5 GB as an actual file, since some layers keep more bits), and the 4B is about 2.5 GB. I also tried a 9B model, and it ran out of GPU memory on the very first training step.

Retraining the whole model wasn’t realistic, so I used LoRA. The original weights stay frozen, and each weight matrix W gets a small correction added on top, W + BA, where B and A are skinny rank-8 matrices. For a 2560 × 2560 matrix that’s 8 × (2560 + 2560) ≈ 41,000 numbers to train instead of 6.5 million, or about 0.6%. Everything I actually trained fits in a 29 MB file.

Teaching it

For training data I wrote a Python generator that spits out thousands of fake conversations, with a fake calendar, fake Notion pages and lots of different ways of saying “set a timer”, each paired with the right tool call and answer. To test a model, I replay Jarvis’s real tool loop on wordings it never saw during training: 34 kinds of question, 10 of each.

What I learned

Fixing the data mattered way more than the model size. Same model, same settings, just cleaned-up data, and four kinds of question went from 0/6 to 6/6.

With only 10 cases per kind, the scores are noisy, since one miss is already 10 points. At an 80% pass rate the binomial spread is √(0.8 × 0.2 / 10) ≈ ±13%, so if you pick the best checkpoint off a single test you end up flattering it. I started re-scoring every pick on a second random seed.

Overfitting showed up too. Training one run for longer made it worse (one kind of question dropped from 9/10 to 2/10), and the validation loss looked fine the whole time. Only the held-out test caught it.

The miss I care about most is being wrong and confident about it. If the model says “I don’t know”, that just costs a cloud call, but if it makes up your exam date, that’s a real bug. I count those separately now.

Smaller job, smaller model

In the end the biggest improvement didn’t come from training harder, it came from giving the model less to do. I moved reminders, alarms and summaries over to plain code and Apple’s own model, which left it with four jobs plus knowing when to hand off. With that narrower job, the 4B model beat the old 8B on the same test while using half the memory.

To be fair, 100% on my own test doesn’t mean it’s perfect, since the test questions come from the same kind of generator as the training data. Next I want to log real questions for a week and test on those.
